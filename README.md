# Jenkins + Terraform + AWS EC2 CI/CD POC

Pipeline: GitHub push -> Jenkins -> static checks -> Terraform validate -> AWS identity -> plan -> mandatory approval -> apply -> EC2 health checks.

## Prerequisites

- Existing Jenkins Docker container with Terraform, AWS CLI v2, Git, Bash, and Python 3 installed.
- Jenkins plugins: Pipeline, Git, GitHub, Pipeline: AWS Steps, AWS Credentials.
- Jenkins global AWS credential ID: `aws-jenkins-terraform`.
- Jenkins job: Pipeline from SCM, Git URL `https://github.com/wavhalkomal/Terraform_Jenkins.git`, branch `main`, script path `Jenkinsfile`.
- Existing EC2 resource in `us-east-1`, Terraform resource address `aws_instance.foo`.
- `terraform init -lockfile=readonly` requires committing `.terraform.lock.hcl` generated by Terraform. Do not delete or ignore the lock file.

## CRITICAL: Preserve existing state BEFORE running a new build

This repository is based on an EC2 instance already created by Jenkins Build #4. Its local Terraform state is in the existing Jenkins workspace. Do not delete the workspace, change the Terraform backend, or run `terraform import` unless you have confirmed state is missing and understand the consequences.

On the Mac:

```bash
docker exec jenkins sh -c 'cd /var/jenkins_home/workspace/terraform-standalone && terraform state list'
mkdir -p ~/terraform-state-backup
docker cp jenkins:/var/jenkins_home/workspace/terraform-standalone/terraform.tfstate ~/terraform-state-backup/terraform.tfstate
chmod 600 ~/terraform-state-backup/terraform.tfstate
```

Expected state resource: `aws_instance.foo`. Do not upload the state backup to GitHub. The state may contain sensitive data.

## Repository preparation

1. Add these files to the existing GitHub repo. Keep the existing EC2 AMI and resource address to avoid replacing the server.
2. Ensure the existing Terraform lock file is committed. If it only exists inside Jenkins, retrieve it first:

   ```bash
   docker cp jenkins:/var/jenkins_home/workspace/terraform-standalone/.terraform.lock.hcl .terraform.lock.hcl
   ```

3. Run `terraform fmt`, then commit/push the files and `.terraform.lock.hcl`.
4. Verify the custom Jenkins image contains `python3` (`docker exec jenkins python3 --version`). If missing, install Python 3 in your custom Docker image and rebuild it; do not install it manually into a running container.
5. In Jenkins job configuration, ensure SCM branch `*/main`, script path `Jenkinsfile`, and the GitHub plugin is installed.
6. Check the first Terraform plan very carefully. It should normally say `0 to add, 0 to change, 0 to destroy` for the already-managed instance. Stop and investigate any replacement or unexpected creation.

## GitHub automatic triggers

The Jenkinsfile enables `githubPush()`, but it does NOT make localhost accessible to GitHub. For a true webhook, expose a secured Jenkins endpoint, configure GitHub repository Settings -> Webhooks -> Add webhook, payload URL `https://YOUR-SECURE-JENKINS-HOST/github-webhook/`, content type `application/json`, push events only. Verify deliveries and Jenkins build causes. Do not expose a local administrator Jenkins UI to the public Internet casually.

For a local-only learning alternative, configure `Poll SCM` in Jenkins Build Triggers with `H/2 * * * *` instead of relying on a webhook. SCM polling is automatic but not event-driven.

## Post-deployment verification

The Bash script waits for `instance-running` and `instance-status-ok`, then checks state, type, Name tag, and region/AZ. This is an AWS infrastructure check, not an application-level health test. SSM/SSH/app endpoint tests can be added later.

Run independently using AWS credentials configured in your shell:

```bash
AWS_REGION=us-east-1 bash post_deployment_check.sh i-0c8d851ce9812586c
```

## Production hardening still needed

- Remote S3 backend with locking, state migration, access controls and encryption.
- Least-privilege IAM credentials (demo currently uses broad permissions).
- PR validation in separate jobs, deploy only from protected main.
- Terraform security scanner (e.g., Checkov or Trivy) and deeper automated tests.
- More robust notifications, deployment rollback/remediation strategy, and a separate approved destroy workflow.
- Restrict GitHub webhook ingress and require TLS; protect Jenkins accounts.

## Caution

The manual approval step is unconditional and limited to Jenkins username `kwavhal`. If your actual Jenkins user ID differs, update `submitter`. The `timeout` is a whole-pipeline limit of 45 minutes, including time waiting for approval.
